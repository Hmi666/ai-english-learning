## 1. 技术选型结论

本项目一期建议采用以下 GitHub 开发脚手架：

> **SmartAdmin：`1024-lab/smart-admin`**

一期使用该仓库中的以下两个工程：

- 后端：`smart-admin-api-java17-springboot3`
- 前端：`smart-admin-web-typescript`

GitHub 地址：<https://github.com/1024-lab/smart-admin>

### 1.1 选择理由

SmartAdmin 与本项目已经确认的技术约束匹配度最高：

- 前端使用 Vue 3、TypeScript、Vite、Pinia 和 Ant Design Vue；
- 后端使用 Java 17 和 Spring Boot 3；
- 持久层使用 MyBatis-Plus；
- 支持 MySQL；
- 提供 Sa-Token 认证授权能力；
- 提供角色、菜单、日志、代码生成和基础管理能力；
- 同一个 GitHub 仓库包含 Java 17 + Spring Boot 3 后端和 Vue 3 TypeScript 前端；
- 项目采用 MIT License，允许在遵守许可证要求的前提下进行修改和商用；
- 后端代码提供 Controller、Service、Manager、DAO 等分层示例，便于按本项目要求落地 MVC；
- 项目规模和基础能力适合在 15 天内裁剪成单体 Web 应用。

### 1.2 一期不采用的能力

SmartAdmin 自带的企业后台能力较多，一期只使用与需求相关的部分：

- 保留：登录、角色权限、用户管理、组织基础能力、操作日志、代码生成辅助能力；
- 按需保留：Redis 会话、文件资源、数据字典、接口文档；
- 暂不启用：工作流、复杂低代码、移动端、短信、邮件、多数据库适配、复杂加密传输和与本项目无关的后台模块。

脚手架中的现有业务模块只能作为基础设施参考，不应直接当作本项目业务需求。学习内容、学习任务、测验和学习记录必须按照本项目 PRD 重新设计。

## 2. GitHub 脚手架调研结果

本次调研以 GitHub 仓库公开信息、README、许可证、目录结构和构建配置为依据。仓库活跃度、版本号和依赖版本会持续变化，以下信息以 2026-10-02 的检索结果为准。

### 2.1 候选方案对比

| 方案 | 技术匹配 | 优点 | 主要风险或不足 | 结论 |
|---|---|---|---|---|
| `1024-lab/smart-admin` | Vue3 + Spring Boot3 + MyBatis-Plus + MySQL | 前后端在同一仓库；提供 Java17/Spring Boot3 版本；有角色权限、日志和代码生成；MIT License；分层结构清晰 | 自带功能较多，需要裁剪；前端采用 Ant Design Vue，不是 Element Plus | **推荐** |
| `dromara/RuoYi-Vue-Plus` 5.X + 配套 `plus-ui` 5.X | Vue3 + Spring Boot3.5 + MyBatis-Plus + MySQL | 社区成熟；权限、数据权限、代码生成和日志能力完整；MIT License | 后端和前端分属不同仓库；模块化和配置项较多；需要匹配 5.X 分支 | 备选一 |
| `jeecgboot/JeecgBoot` | Vue3 + Spring Boot + MyBatis-Plus + MySQL | 社区规模大；代码生成器和低代码能力强；Apache License 2.0 | 当前主线包含 Spring Boot 4、微服务、AI 和低代码大量能力；对 15 天一期过重 | 不建议一期采用 |
| `Leo-Flynn/scaffold` | Vue3 + Spring Boot3 + MyBatis-Plus + MySQL | 目录简单，学习成本低 | GitHub 公开信息显示项目规模很小，未提供成熟 RBAC 和完整操作日志；许可证信息缺失 | 不采用 |

### 2.2 RuoYi-Vue-Plus 备选说明

RuoYi-Vue-Plus 是可靠的备选方案。若团队已经熟悉 RuoYi 生态，可以使用：

- 后端：<https://github.com/dromara/RuoYi-Vue-Plus/tree/5.X>
- 前端：<https://github.com/CrazyLionCat/plus-ui/tree/5.X>

5.X 分支当前配置为 Java 17、Spring Boot 3.5.x 和 MyBatis-Plus 3.5.x，前端为 Vue 3、TypeScript、Vite 和 Element Plus。选择 5.X 而不是当前 6.X，是因为当前 6.X 后端已经切换到 Spring Boot 4 和 JDK 21，与 15 天一期不需要的升级风险不匹配。

本项目仍优先选择 SmartAdmin，主要原因是后端和前端位于同一个仓库，并且仓库直接提供 `java17-springboot3` 与 TypeScript 前端目录，初始化和版本对应关系更简单。

### 2.3 JeecgBoot 不作为一期基线的原因

JeecgBoot 的社区和功能规模很大，适合作为企业级低代码平台或大型管理系统基础平台。但本项目一期只有单学校、三角色和学习任务闭环，使用其主线会引入：

- 微服务和 Spring Cloud 相关配置；
- 低代码、报表、大屏和 AI 模块；
- 更多中间件和部署组件；
- 更高的学习和裁剪成本。

如果未来项目扩展为多学校 SaaS 平台或需要大量低代码表单，JeecgBoot 可以作为后续重新评估的候选方案，但不作为本期 15 天开发基线。

## 4. 总体架构

### 4.1 架构形式

一期采用：

> **前后端分离 + 单体部署 + Spring MVC + MySQL + MyBatis-Plus**

不采用微服务。前端单独开发和构建，后端以一个 Spring Boot 应用运行。这样可以降低 15 天内的部署、联调和测试成本。

```text
┌─────────────────────────────────────────────┐
│                  Web 浏览器                  │
│          Vue 3 + TypeScript + Ant Design Vue │
└──────────────────────┬──────────────────────┘
                       │ HTTPS / REST JSON
                       ▼
┌─────────────────────────────────────────────┐
│              Spring Boot 单体应用            │
│                                             │
│  Controller  →  Service  →  Mapper/DAO      │
│       │              │            │         │
│       │              │            └─ MyBatis-Plus
│       │              └─ 事务、业务规则、权限范围
│       └─ 参数校验、接口协议、统一响应         │
│                                             │
│  Sa-Token / 日志 / OpenAPI / 全局异常处理    │
└──────────────────────┬──────────────────────┘
                       │ JDBC
                       ▼
┌─────────────────────────────────────────────┐
│                    MySQL 8                   │
│       组织、账号、内容、任务、测验、记录      │
└─────────────────────────────────────────────┘

可选：Redis 用于登录会话或缓存，不承载一期核心业务数据。
```

### 4.2 部署形态

开发环境：

- Vue Vite 开发服务器；
- Spring Boot 本地运行；
- MySQL 8；
- Redis 仅在脚手架认证配置需要时启动；
- Vite 代理 `/api` 到 Spring Boot。

验收环境：

- Nginx 提供前端静态资源；
- Spring Boot 以 JAR 运行；
- Nginx 将 `/api` 反向代理到后端；
- MySQL 独立运行；
- 可使用 Docker Compose 编排 MySQL、Redis、后端和 Nginx。

一期不部署网关、注册中心、配置中心、消息队列、微服务集群和分布式链路追踪。

## 5. MVC 与后端代码规范

### 5.1 分层职责

本项目后端使用经典 MVC 思路，并结合脚手架已有的分层结构：

| 层次 | 目录建议 | 职责 | 禁止事项 |
|---|---|---|---|
| Controller | `controller` | 接收请求、参数校验、权限入口、调用 Service、返回 VO | 不写业务规则，不直接操作 Mapper |
| Service | `service` | 编排业务流程、事务边界、业务校验、数据权限校验 | 不返回数据库实体作为公共接口契约 |
| Manager | `manager`，按需使用 | 处理跨 Service 的领域能力或外部资源调用 | 不能成为无规则的代码中转层 |
| Mapper/DAO | `mapper`、`dao` | MyBatis-Plus CRUD、分页和必要的自定义 SQL | 不处理用户权限和页面逻辑 |
| Entity | `domain/entity` | 数据库映射对象 | 不直接作为前端接口输出 |
| DTO | `domain/dto` | 接收前端请求 | 不携带数据库无关的页面状态 |
| VO | `domain/vo` | 面向前端返回结果 | 不暴露密码、内部审计字段和不必要的关联对象 |
| Converter | `convert` | Entity、DTO、VO 转换 | 不在转换器中写业务判断 |

对于一期简单功能，可以使用 `Controller → Service → Mapper` 三层；只有存在跨模块或外部资源编排时再增加 Manager，避免为了形式复制四层结构。

### 5.2 业务模块划分

建议在后端新建独立的教育业务模块，避免直接修改脚手架系统模块：

```text
smart-admin-api-java17-springboot3/
├── sa-base/                         # 脚手架公共基础能力
├── sa-admin/                        # 脚手架系统管理能力
└── sa-english/                      # 本项目一期业务模块
    └── src/main/java/.../english/
        ├── controller/
        │   ├── AuthController.java
        │   ├── OrganizationController.java
        │   ├── ContentController.java
        │   ├── TaskController.java
        │   ├── QuizController.java
        │   ├── LearningRecordController.java
        │   └── DashboardController.java
        ├── service/
        ├── manager/
        ├── mapper/
        ├── entity/
        ├── dto/
        ├── vo/
        ├── convert/
        └── enums/
```

如果团队决定不新增 Maven 模块，也必须保持 `english` 业务包与系统管理包分离。

### 5.3 事务边界

以下操作必须由 Service 层开启事务：

- 创建任务及任务班级关系；
- 创建测验及测验题目、测验班级关系；
- 提交测验、保存答题记录、计算成绩和生成错题记录；
- 停用账号及相关权限状态更新；
- 下架内容时涉及的关联状态变更。

测验提交接口必须考虑重复提交。建议通过数据库唯一约束和 Service 层校验双重保证“一名学生对同一测验只能提交一次”。

## 7. 数据库与 ORM 选型约束

### 7.1 数据库

- 使用 MySQL 8.0 或更高版本；
- 默认字符集使用 `utf8mb4`；
- 默认排序规则使用团队确认的 `utf8mb4` 排序规则；
- 所有表必须包含主键；
- 业务表建议包含 `created_at`、`updated_at`、`created_by`、`updated_by`、`deleted` 等审计或逻辑删除字段；
- 不将姓名、班级名称等容易变化的展示文本作为唯一关联依据；
- 关键关系表必须建立唯一约束和外键索引对应的普通索引；
- 是否使用数据库外键由技术负责人结合脚手架和部署策略确认，但应用层必须保证引用完整性。

### 7.2 MyBatis-Plus

MyBatis-Plus 的使用约束：

- 简单 CRUD 使用 `BaseMapper`；
- 分页使用统一分页插件和统一分页响应对象；
- 复杂统计查询使用明确的 `QueryWrapper` 或 XML SQL；
- SQL 只放在 Mapper/XML，不在 Service 或 Controller 中拼接；
- 所有 SQL 必须限制学校、班级或学生的数据范围；
- 不为了使用代码生成器而牺牲业务模型清晰度；
- 对测验提交、任务完成等写操作增加幂等或唯一性保护；
- 禁止使用未经审查的全量查询作为管理统计实现。

### 7.3 核心数据对象

数据库设计至少覆盖以下业务对象：

| 对象 | 说明 |
|---|---|
| `school` | 单学校基础信息，作为业务数据归属 |
| `grade` | 年级信息 |
| `class` | 班级信息 |
| `user` | 管理员、教师、学生账号 |
| `role` | 角色信息，优先复用脚手架角色体系 |
| `user_role` | 用户和角色关系 |
| `teacher_class` | 教师和班级关系 |
| `student_class` | 学生和班级关系 |
| `learning_content` | 词汇、语法、阅读和可选听力内容 |
| `question` | 单选题和判断题 |
| `content_question` | 内容和练习题关系 |
| `learning_task` | 教师布置的学习任务 |
| `task_class` | 任务和目标班级关系 |
| `learning_record` | 学生学习完成记录 |
| `quiz` | 固定客观题测验 |
| `quiz_question` | 测验和题目关系 |
| `quiz_class` | 测验和目标班级关系 |
| `quiz_attempt` | 学生测验提交记录 |
| `quiz_answer` | 学生逐题作答记录 |
| `operation_log` | 关键操作记录，优先复用脚手架日志体系 |

完整字段、索引、唯一约束和状态枚举在数据库设计文档中确定，本文件不替代数据库设计文档。

### 7.4 数据权限实现建议

一期是单学校系统，但仍采用显式数据范围过滤：

- 管理员：按 `school_id` 过滤；
- 教师：通过 `teacher_class` 过滤 `class_id`；
- 学生：通过当前用户 ID 过滤个人记录；
- 教师查看学生数据时，必须同时校验教师与目标班级的关联；
- 学生提交任务或测验时，必须校验学生与目标班级的关联；
- 不信任前端传入的 `school_id`、`class_id` 或 `student_id`，这些值必须由当前用户权限范围推导或再次校验。

## 8. 认证、授权与安全

### 8.1 认证方案

使用 SmartAdmin 已集成的 Sa-Token：

- 账号密码登录；
- 登录成功后签发令牌；
- 请求通过统一拦截器或框架机制校验令牌；
- 令牌失效后返回 401；
- 首次登录状态由用户字段控制；
- 管理员重置密码后，使该用户已有令牌失效；
- 密码使用安全哈希保存，不保存明文密码。

一期不接入统一身份认证、第三方登录和短信验证码登录。

### 8.2 授权方案

使用 RBAC，即基于角色的访问控制：

- `admin`：学校管理员；
- `teacher`：教师；
- `student`：学生。

授权分两层：

1. **功能权限**：是否可以访问菜单、页面和接口；
2. **数据权限**：访问哪些学校、班级、学生和业务记录。

接口权限必须同时检查功能权限和数据范围。仅检查 `teacher` 角色而不检查班级关系是不合格的权限实现。

### 8.3 未成年人数据要求

本项目涉及小学生学习数据，一期必须：

- 只收集完成需求所需的数据；
- 不在日志中记录密码和完整敏感请求体；
- 学生详细记录只向本人和授权教师开放；
- 测试数据使用虚构姓名，不使用真实未成年人信息；
- 上线前由项目负责人确认适用的隐私和未成年人保护要求。

## 9. API 与接口规范

### 9.1 接口风格

- 使用 REST 风格 HTTP API；
- 数据格式使用 JSON；
- API 路径统一以 `/api` 开头；
- 接口版本一期可以使用 `/api/v1`；
- 使用统一响应结构；
- 使用统一错误码和错误消息；
- 使用 Knife4j 生成接口文档；
- 分页、排序和筛选参数使用统一命名。

### 9.2 接口模块建议

```text
/api/v1/auth                  # 登录、退出、修改密码
/api/v1/organization          # 学校、年级、班级、账号关系
/api/v1/content               # 学习内容
/api/v1/questions             # 题目
/api/v1/tasks                 # 学习任务
/api/v1/quizzes               # 测验、题目和提交
/api/v1/learning-records      # 学习记录和错题
/api/v1/dashboard             # 基础统计
/api/v1/operation-logs        # 操作日志
```

### 9.3 统一响应建议

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "traceId": "optional-trace-id"
}
```

具体字段名以脚手架既有规范为准。新模块不应同时引入第二套响应格式。

### 9.4 接口文档最低要求

每个接口至少说明：

- 请求方法和路径；
- 登录和角色要求；
- 请求参数及必填项；
- 返回字段；
- 错误码；
- 数据权限范围；
- 是否具备幂等要求。

## 12. 技术风险与控制措施

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 脚手架自带模块过多 | 学习和裁剪成本增加 | 只保留登录、权限、用户、日志和基础组件；不直接启用无关模块 |
| Spring Boot 或前端依赖自动升级 | 构建不稳定、返工 | 固定版本、提交锁文件，不在一期中升级大版本 |
| 数据权限实现不完整 | 学生数据越权 | 后端按用户关系过滤；单独编写越权测试用例 |
| 直接使用脚手架表结构 | 与学习业务不匹配 | 业务数据重新建模，脚手架只复用系统管理表和基础能力 |
| 代码生成器生成代码过多 | 业务逻辑混乱 | 只用于基础 CRUD，生成后人工审查并补充权限和事务 |
| 题目提交重复写入 | 成绩和错题错误 | Service 事务 + 唯一约束 + 重复提交测试 |
| 前后端依赖版本不匹配 | 联调失败 | 后端和前端使用同一脚手架版本线，初始化时锁定 SHA |
| 测试使用真实学生数据 | 隐私风险 | 使用虚构测试数据，禁止提交真实个人信息 |
| Redis 成为不必要依赖 | 部署复杂 | 只用于脚手架确需的会话/缓存；一期不把业务功能建立在 Redis 上 |
